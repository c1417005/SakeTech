# KUMU 店舗マップ作成機能 実装仕様 v0.2

> [!summary] 30秒まとめ
> ==10×8固定グリッドに、棚・レジ・出入口のオブジェクトを配置し、マップ全体を丸ごと POST する==。棚は 1×N プリセットで ==表裏（facing）を持つ==。人と棚の隣接判定はバックエンドが持ち、判定範囲は棚が向いている側のみ。フロントは「描いて送る」「返ってきた人を描く」に専念する。

親ドキュメント: [[2026-08-14 KUMU フロントエンド要件定義 PRD]]

> [!note] v0.1 からの変更
> 棚に**表裏**を追加。銘柄は**棚の属性**に。オブジェクト種別に**レジ・出入口**を追加。保存は**自動＋ボタン併用**。銘柄検索は**石川県に限定**。

---

## 決定事項

| 項目 | 決定 |
|---|---|
| グリッドサイズ | **10×8 固定** |
| オブジェクト種別 | **棚 / レジ / 出入口** |
| 棚のサイズ | **1×2 / 1×3 / 1×4 のプリセットのみ**。自由リサイズなし |
| 棚の向き | ==`facing` で north / south / east / west== |
| 銘柄 | ==棚の属性として持つ==。独立オブジェクトにしない |
| 配置方法 | ドラッグ&ドロップ。削除可 |
| 保存 | **自動保存＋保存ボタン併用** |
| 銘柄検索 | ==石川県の銘柄に限定== |
| 人の座標 | セル単位の整数 |
| 「棚を見ている」判定 | ==バックエンドが持つ==。棚が向いている側の隣接セルのみ |
| POST の単位 | マップ全体を丸ごと |
| ポーリング | `GET /sessions` を10秒間隔 |

---

## 表裏（facing）を持たせる理由

1. **背中合わせの棚**を置く店がある。裏の概念がないと判定範囲が重なって扱えない
2. **壁際の棚**は裏側が壁なのに、4近傍だと壁側も判定範囲に入ってしまう
3. 棚Aの裏にいる人は、棚Aを見ていない

> [!tip] 副次的な効果
> `facing` が north / south なら棚は横向き、east / west なら縦向きだと分かる。==`orientation` フィールドが不要になり、1つのフィールドで軸と向きを兼ねる==。

### それでも残る重なり

**通路の両側の棚が、どちらも通路を向いている場合**、人が通路に立つと2つの棚の前に同時にいることになる。これは現実にも起きる状況（実際どちらを見ているかは体の向き次第）。

対応は2案。==バックエンド担当と決める==。

- `shelf_ids` を配列で返す（フロントは「棚Aか棚Bのあたり」と表示）
- 最も近い1つに決め打ちする

---

## 設計上の簡略化

グリッドを「セルを塗って種類を決めるもの」として作る必要は**ない**。

オブジェクトをドラッグ配置する方式なら、グリッドは単なる**背景の方眼**でよく、保持すべきデータは ==オブジェクトの配列だけ== になる。セル1つずつに種別を持たせる 80要素の配列は不要。

保持する状態は `objects[]` 1つ。ドラッグ中の一時状態のみ別に持つ。

---

## データ形式（バックエンドへの提案）

### POST /map — マップの保存

```json
{
  "grid": { "width": 10, "height": 8 },
  "objects": [
    {
      "type": "shelf",
      "id": "shelf-a",
      "name": "棚A",
      "x": 2, "y": 1,
      "length": 3,
      "facing": "north",
      "brand_ids": [1234, 5678]
    },
    {
      "type": "shelf",
      "id": "shelf-b",
      "name": "棚B",
      "x": 2, "y": 2,
      "length": 3,
      "facing": "south",
      "brand_ids": [9012]
    },
    { "type": "entrance", "id": "ent-1", "x": 0, "y": 7 },
    { "type": "register", "id": "reg-1", "x": 9, "y": 7 }
  ]
}
```

- `x`, `y` は起点セル（左上）
- `facing` が north / south なら `x` 方向に、east / west なら `y` 方向に `length` 分伸びる
- `brand_ids` はさけのわの銘柄 ID を想定（要合意）
- レジ・出入口は 1セル固定。`length` と `facing` を持たない

### GET /map — 読み戻し

POST と同じ形を返す。編集の続きができるようにするため。

### GET /sessions — 来店者リスト（10秒ポーリング）

```json
[
  {
    "session_id": "a1b2",
    "x": 3, "y": 2,
    "state": "hesitating",
    "dwell_sec": 42,
    "shelf_id": "shelf-a"
  }
]
```

`shelf_id` は**バックエンドが隣接判定した結果**。フロントは判定せず、この値をそのまま使う。

## 保存の挙動

自動保存とボタンを併用する。

| タイミング | 動作 |
|---|---|
| 操作後、一定時間（2秒程度）操作がない | 自動で POST |
| 保存ボタン押下 | 即時 POST |

- ==自動保存のたびにトーストを出さない==。うるさくて店主が嫌がる
- 代わりに「保存済み / 保存中 / 未保存」の状態を画面の隅に控えめに常時表示する
- 保存ボタンは、自動保存を待たずに確定させたい人のための安心材料として置く

---

## POST 後の表示分岐

メモにあった「200 なら成功、403 なら失敗」の部分。

| ステータス | 画面表示 |
|---|---|
| 200 / 201 | 「保存済み」＋保存時刻 |
| 400 | 「マップの内容に問題があります」＋該当箇所 |
| 409 | 「他の端末で更新されています」 |
| 403 / 401 | 「保存の権限がありません」 |
| 5xx / タイムアウト | 「保存できませんでした」＋==編集内容は保持し、次の自動保存で再試行== |

> [!warning] 403 は要確認
> 認証機能がない MVP で 403（権限なし）が返る状況が想像しづらい。バリデーションエラーなら 400、更新衝突なら 409 が自然。==実際にどのコードが返るかをバックエンド担当と確認する==。存在しないコードのハンドリングを書いても意味がない。

共通方針として、==ステータスコードの数字をそのまま画面に出さない==。IT に不慣れな店員には意味がない。

## マップと JSON の関係（実装の考え方）

画面に見えているマップと JSON は**同じもの**。絵は JSON の見え方にすぎない。

1. アプリは `objects[]` を状態として持つ
2. 配列を見て絵を描く
3. ドラッグされたら配列の数値を書き換える → 2 が走って絵が描き直される

> [!tip] 逆向きは起きない
> 「絵を動かして、後から JSON を組み立てる」のではない。==常に配列が正で、画面はその写し==。これが「データ駆動で描画する」の中身。
>
> だから保存は `JSON.stringify` して POST するだけ、読み込みは受け取った配列を状態に入れるだけで済み、==保存機能を別途作る必要がない==。

## 実装順（フロント単独で進められる順序）

1. **10×8 グリッドの描画** — 背景の方眼だけ
2. **オブジェクトのパレット＋ドラッグ配置** — プリセット選択、facing 切替、削除、重なり・範囲外の禁止
3. **自動保存＋保存ボタン → POST → ステータス分岐表示** — モックサーバー相手でよい
4. **GET /map で読み戻し**
5. **銘柄の紐づけ UI** — さけのわの石川県銘柄を検索
6. **GET /sessions ポーリング＋人の描画**

> [!tip] 3 までで一区切り
> ==1〜3 はバックエンドが1行も書けていなくても完成させられる==。モックサーバーを立てるか、`fetch` をスタブに差し替えれば動く。

## 実装時の注意

### 点がワープする問題

整数座標＋10秒ポーリングなので、人の点は**10秒ごとに瞬間移動**する。店主から見ると何が起きたか分からない。CSS トランジションで数百ミリ秒かけて移動させるだけで体感が変わる。==実装時に忘れやすいので最初から入れる==。

### 重なり判定

棚を 1×N プリセットに限定したので、判定は単純な矩形の重なりで済む。占有セルの集合を作って交差を見るだけ。

### facing の UI 表現

棚がどちらを向いているかが**一目で分かる**必要がある。矢印アイコン、または向いている辺だけ色を変えるなど。向きを間違えて配置すると判定が丸ごとずれるため、==編集画面で判定範囲をうっすら可視化する==と事故が減る。

## バックエンド担当と合意すべきこと

- [ ] エンドポイント名（`/map`, `/sessions` でよいか）
- [ ] ==成功・失敗時に実際に返るステータスコード==（特に 403 の実体）
- [ ] `facing` の値の持ち方（north / south / east / west でよいか）
- [ ] ==通路の両側から向かい合う棚の扱い==（`shelf_ids` 配列にするか、最も近い1つか）
- [ ] `brand_ids` はさけのわの ID をそのまま使うか、内部 ID を振るか
- [ ] マップは1件のみか、複数保存して切り替えるか
- [ ] 自動保存の頻度に耐えられるか（レート制限の有無）
