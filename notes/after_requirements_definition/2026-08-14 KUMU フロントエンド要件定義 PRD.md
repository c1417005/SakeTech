# KUMU フロントエンド要件定義 (PRD v0.1)

> [!summary] 30秒まとめ
> 酒販店の店員向けデスクトップ画面の要件。==Webアプリで実装==し、店内マップ1枚に来店者を表示、行動から推定した好みタグを添える。狙いは「==足の動きを味の語彙に翻訳する==」こと。対話で確定した内容を反映し、未確定箇所は TBD を残してある。

## 2. 背景・目的

### 背景

[[07-04ハッカソン 課題発見まとめ]] の3層モデルのうち、KUMU が扱うのは**第3層「酒販店 ↔ 消費者の分断」**。

- 酒販店は12年で7万→3万件に半減、10年後は2万件の予測
- 売上構成は飲食店8割・一般消費者2割で、そもそも一般客との接点が薄い
- [[インプットセッション]] の瀬戸氏いわく「新規顧客の獲得が難しい」「薦め方のトークが課題」

### 解決したい課題

消費者は自分の好みを**言語化する語彙を持っていない**。だから「辛口ください」としか言えない。一方で辛口には種類があり、店員はそこから深掘りできずに終わる。

> [!note] 中心となる仮説
> ==口は語彙を持たないが、足は正直に動く。== 店内での滞留・回遊は、本人が言語化できない好みを表している。

### 目的（Why）

**行動を味の語彙に翻訳し、店員が声をかけるきっかけと、その第一声の中身を同時に渡す。**

### 成功イメージ

- 店主が「4番棚の赤い服の人、そろそろ声をかけるか」と自然に判断できる
- 新人が「香り高いのがお好きですか」と、根拠のある第一声を出せる
- 消費者が「自分でも言葉にできなかった好み」を提示され、買って帰る

## 3. スコープ

### 対象ユーザー

酒販店の店員。主役は**店主・ベテラン**、副次的に**新人アルバイト**。共通する制約は ==IT に不慣れ== であること。

### 対象プラットフォーム

**Web アプリ（PC ブラウザ）**。デスクトップアプリ（Electron / Tauri）は採用しない。

> [!note] Web を選んだ理由
> 1. 要件はクラウドから取得したデータを描画するだけで、ブラウザにできないことがない
> 2. Electron はビルド・署名・配布で当日の時間が溶ける
> 3. デプロイして==URL を審査員に渡せる==
> 4. 見た目だけデスクトップアプリらしくしたいなら PWA 化で足りる

前提として、通信は **スマホ → クラウド → PC** に一本化する。同一 Wi-Fi 内での端末間直通信は、==会場ネットワークで遮断される事故が多い==ため採用しない。

### スコープに含めるもの

- リアルタイム店内マップ（主役画面）
- 来店者マーカーと客カード（見た目タグ・推定タグ）
- 棚と在庫銘柄の表示
- モックデータ再生モード
- 通信エラー時の表示分岐

### スコープ外（やらないこと）

| 項目 | 理由 |
|---|---|
| リピーター識別・顔認証 | 精度リスクと法務コスト。詳細は [[2026-08-14 KUMU 顧客識別レベルと好み推定の判断材料]] |
| 会員登録・ログイン | MVP に不要 |
| 来店後の分析ダッシュボード | 主役はリアルタイム |
| POS・在庫システム連携 | 範囲外 |
| 多店舗対応 | 1店舗固定 |
| iOS 側の UI | 別担当 |
| 店舗マップ登録画面 | ==方針変更。stretch ではなく最初に着手==。詳細は [[2026-08-14 KUMU 店舗マップ作成機能 実装仕様]] |

## 4. ユーザーペルソナ

### P1: 店主（主役）

| 項目 | 内容 |
|---|---|
| 属性 | 50〜60代、酒販店店主。接客歴20年以上 |
| スキル | 酒の知識はプロ級。==PC はメールと発注システムのみ== |
| 利用シーン | レジ横の PC に常時表示。接客の合間に視線を向ける |
| ニーズ | 声をかけるべきタイミングを逃したくない |
| ペイン | 新しいツールの操作を覚える余裕がない。手が離せない時間が長い |

### P2: 新人アルバイト（副）

| 項目 | 内容 |
|---|---|
| 属性 | 20代、勤務2ヶ月。日本酒の知識はほぼない |
| 利用シーン | 声をかける前に画面を見て、話す内容を用意する |
| ニーズ | 何を言えばいいか分からない不安を減らしたい |
| ペイン | 銘柄と味の対応が頭に入っていない |

> [!warning] 2人のペルソナが同じ制約を共有する
> 熟練度は真逆だが、==どちらも IT に不慣れ==。ゆえに UI の方針は「情報を減らす」ではなく「**操作を覚えなくても使える**」。

## 5. ユースケース / ユーザーストーリー

- **UC1**: 店主が接客の合間に画面を見たとき、迷っている客が視覚的に目立つことで、声をかけるタイミングを掴める
- **UC2**: 新人が声をかける前に客カードを見ることで、推定された好みを踏まえた第一声を出せる
- **UC3**: 店員が「赤い上着・黒いカバン」という見た目タグを見ることで、==マップ上の点と店内の実際の人物を照合==できる
- **UC4**: 店員が棚をクリックしたとき、その棚の銘柄一覧が出ることで、提案する具体的な商品を選べる
- **UC5**（stretch）: 店主が棚の配置を変えたとき、登録画面から座標を更新できる

## 6. 機能要件

### F-1: リアルタイム店内マップ

- **概要**: 店舗を x, y 座標のグリッドで描画し、通路・棚・来店者を重ねて表示する
- **詳細仕様**:
  - マップは ==JSON データから描画==する。画面にハードコードしない（stretch の登録画面を後付けするため）
  - `GET /sessions` を **10秒間隔でポーリング**し、自動更新する
  - 更新ボタンは置かない（ゼロ操作 UI）
- **入力**: マップ定義 JSON、`GET /sessions` レスポンス
- **出力**: 描画されたマップ
- **例外**: マップ JSON が不正な場合はエラー画面。来店者0人の場合は「現在、来店者はいません」を明示

### F-2: 来店者マーカーと状態表現

- **概要**: 来店者を点で表示し、状態に応じて見た目を変える
- **詳細仕様**:
  - 状態は `moving`（移動中） / `viewing`（見ている） / `hesitating`（迷っている）の3種
  - `hesitating` はマーカーを拡大＋ゆるやかな脈動で目立たせる
  - ==色だけで状態を区別しない==。文字ラベルを必ず併記する
  - トースト通知・音は出さない（画面の変化のみ）
- **入力**: `state`, `x`, `y`, `dwell_sec`
- **例外**: 座標がマップ範囲外の場合は描画せず、件数のみカウント

### F-3: 客カード

- **概要**: マーカーに付随して、見た目タグ・推定タグ・滞在時間を表示する
- **詳細仕様**:
  - タグを**2群に分けて表示**する
    - **見た目タグ**（赤い上着、黒いカバン）= 観測した事実 → 実線・無彩色
    - **推定タグ**（香り高い、やや甘口）= 推定 → 破線・色付き
  - 推定タグは ==確信度順に最大3個==まで
  - 推定には**根拠を1行**添える（例: 手取川、天狗舞を長く見ています）
  - 表示語彙は平易語のみ。詳細パネルでのみ「香り高い（薫酒タイプ）」と専門語を併記する
  - 確信度が `low` の場合は「推定中」と表示し、断定しない
- **例外**: `profile` が欠損している場合はタグ群ごと非表示。空タグは出さない

> [!warning] 2群を分ける理由
> 「赤い上着」は間違えようがないが「甘口派」は外れうる。同じ見た目で並べると、==新人が両方を同じ確度で信じてしまう==。

### F-4: 棚・商品レイヤ

- **概要**: 棚をクリックすると、その棚の銘柄一覧と味の特徴を表示する
- **詳細仕様**: 銘柄名＋4タイプ分類（薫酒・爽酒・醇酒・熟酒）＋平易語タグ
- **例外**: さけのわにフレーバーデータが存在しない銘柄は、銘柄名のみ表示する

### F-5: モックデータ再生モード

- **概要**: バックエンド不在でも、擬似データで画面を動かせるモード
- **詳細仕様**:
  - 実 API と同一形式の JSON をタイムライン再生する
  - URL パラメータ等で切り替える
  - デモシナリオ（入店 → 1〜3番棚を回遊 → 4番棚で迷う）を再現できること
- **重要度**: ==最優先で着手する==。当日のデモは画面内シミュレーションであり、通信事故時のフォールバックにもなる

### F-6: 接続状態表示とエラー処理

- **概要**: 通信の成否を店員に分かる言葉で伝える
- **詳細仕様**:

| ステータス | 表示 |
|---|---|
| 200 | 通常表示。最終更新時刻を小さく表示 |
| 403 / 401 | 「接続の許可がありません」 |
| 5xx / タイムアウト | 「接続できません。再試行中です」＋直前の状態を保持 |

- ==エラーコードをそのまま出さない==。IT に不慣れな店員には意味がない

### F-7（stretch）: 店舗マップ登録画面

- **概要**: グリッド上でセルに通路・棚を割り当て、棚に銘柄を紐づける
- **前提**: F-1 のマップ描画がデータ駆動であること

## 7. 非機能要件

| 分類 | 要件 |
|---|---|
| パフォーマンス | 初期表示2秒以内。ポーリング10秒間隔。同時表示は来店者20人程度を想定 |
| 常時稼働 | 営業時間中つけっぱなし前提。==メモリリークを起こさない==こと（ポーリングとタイマの後始末） |
| セキュリティ | MVP では認証なし。ローカル/限定URLでの運用を前提とする |
| 個人情報 | 顔特徴量は保存しない。服装タグ等は退店時に破棄。撮影告知の掲示は運用側の責務 |
| ライセンス表示 | ==さけのわデータの帰属表示を画面内に常設==（利用規約上の必須要件） |
| 対応ブラウザ | Chrome 最新版のみ（当日デモ環境に限定） |
| アクセシビリティ | 色のみに依存しない。文字サイズは既定より大きめ。クリック対象を大きく取る |

## 8. 画面・UI/UX

### 主要画面一覧

1. **店内マップ画面**（唯一の常時表示画面）
2. 客カード（マップ上のオーバーレイ。別画面にしない）
3. 棚詳細パネル（同上）
4. マップ登録画面（stretch）

### UX 原則

> [!tip] やってほしいこと
> - **1画面で完結させる**。タブ・階層・メニューを作らない →ここはもう少し考えてもいいかも。
> - **操作なしで機能する**。見ているだけで更新される
> - **文字で書く**。アイコンだけで意味を伝えない
> - **推定は推定として見せる**。破線・確信度・根拠をセットにする

> [!warning] やってほしくないこと
> - 更新ボタンを押さないと最新にならない
> - エラーコードや専門用語をそのまま出す
> - 推定を断定として表示する
> - 音やポップアップで接客を中断させる

## 9. データ要件

### 主要エンティティ

| エンティティ | 主な項目 |
|---|---|
| `store_map` | grid_width, grid_height, cells[] |
| `cell` | x, y, type（通路 / 棚 / レジ）, shelf_id |
| `shelf` | id, name, product_ids[] |
| `product` | brand_id, name, f1〜f6（さけのわフレーバー）, type4 |
| `session` | session_id, x, y, state, dwell_sec, elapsed_sec |
| `appearance_tags` | session_id, tags[]（服装の色など。観測値） |
| `profile` | session_id, tags[], confidence, basis[] |

### データフロー

`iOS カメラ` → `クラウドサーバー`（滞留イベント記録・好み推定） → `GET /sessions` → `店員向け Web`

推定計算は ==サーバー側で行う==。フロントは表示に専念し、ロジック変更でフロントを触らずに済む。

### 外部サービス連携

**さけのわデータ** — `https://muro.sakenowa.com/sakenowa-data/api/` 配下。銘柄・蔵元・地域・フレーバーチャート・フレーバータグを提供。

フレーバーチャートは6軸（f1 華やか / f2 芳醇 / f3 重厚 / f4 穏やか / f5 ドライ / f6 軽快）。このうち4軸が4タイプ分類に対応するため、==4タイプは別途入力せず数値から導出できる==。

> [!warning] さけのわの制約
> - 銘柄(brand)単位であり、同じ銘柄の純米と大吟醸を区別しない
> - フレーバーチャートが存在しない銘柄がある → 欠損時の表示を決めること
> - 全件一括で返る形式。==フロントから直接叩かず、バックエンドで取得・保存する==
> - 帰属表示が必須

デモ用データは、地域一覧から**石川県の銘柄を抽出して架空の店の棚を構成する**。石川の地酒は濃厚芳醇＝醇酒ゾーンに寄るはずで、[[インプットセッション]] の内容と地続きのストーリーになる。

### ログ設計

- ポーリングの成否と応答時間
- 客カードを開いた回数（どの機能が実際に見られたか）
- モックモードか実データかの区別

## 10. リリース計画

本番まで1ヶ月以上。週次のマイルストーンを置く。

| 週 | 目標 |
|---|---|
| W1 | ==API レスポンス形式をバックエンドと確定==。モックデータ再生モード（F-5）を先に作る |
| W2 | マップ描画（F-1）＋マーカー状態表現（F-2） |
| W3 | 客カード（F-3）＋棚詳細（F-4）＋エラー処理（F-6） |
| W4 | 実 API 結合、デモシナリオ作り込み、リハーサル |
| 余裕があれば | マップ登録画面（F-7） |

> [!tip] 2人体制での進め方
> ==W1 で API の形さえ決まれば、フロントはバックエンドの完成を待たずに走り切れる==。最初の1週間の合意が全体の速度を決める。

当日は**モックモードを必ず起動可能な状態にしておく**。実 API が落ちても、切り替えてデモを継続できる。

## 11. リスク・課題

| リスク | 内容 | 対応方針 |
|---|---|---|
| **見逃し** | 画面の変化だけでは、接客中の店員が気づかない | MVP では許容。「気づいた時に分かればよい」と割り切る。11章に正直に書き、審査で聞かれたら将来の通知設計として答える |
| **推定精度** | 好みタグが的外れだと信頼を失う | 確信度・根拠を必ず併記し、断定しない。低確信度は「推定中」 |
| **データ欠損** | さけのわにフレーバーがない銘柄 | 銘柄名のみ表示にフォールバック |
| **API 待ち** | バックエンド未完成でフロントが止まる | モックモードを最優先で実装 |
| **会場ネットワーク** | 通信が不安定 | クラウド一本化＋モックフォールバック |
| **プライバシーの質問** | 審査で必ず聞かれる | 匿名MVP・特徴量非保存を明確に答えられるようにしておく |
| **コンセプトの散逸** | [[アイデア出し]] には育成ゲーム等の別路線が残っている | KUMU は店内接客支援に一本化する |

### 未確定事項（TBD）

- [ ] グリッドの粒度（何マス × 何マスか）
- [ ] 服装タグの抽出項目（色のみか、持ち物も含むか）
