# KUMU 顧客識別レベルと好み推定の判断材料

> [!summary] 30秒まとめ
> バックエンド担当が判断するための材料。論点は2つ。==①お客さんをどのレベルで識別するか（匿名／会員／顔Re-ID）==、==②「甘口派っぽい」という好み推定をどのデータで、どこで計算するか==。フロント側の要求は「客の点に、根拠と確信度つきの好みタグが付随して見えること」。

---

## 論点1: 顧客識別レベル

### 3案の比較

| | A. 完全匿名 | B. 匿名＋任意会員紐づけ | C. リピーター識別（顔Re-ID） |
|---|---|---|---|
| **識別の粒度** | 来店セッション単位。退店で消滅 | 基本は匿名、QR等を読んだ人だけ永続 | 人物単位で永続 |
| **主エンティティ** | `session` | `session` ＋ 任意の `customer` | `customer`（`session` がぶら下がる） |
| **技術的にやること** | 同一フレーム内の人物追跡のみ | A＋会員コード読み取り導線 | 顔特徴量抽出＋人物再同定 |
| **精度リスク** | 低 | 低 | ==高。誤認識でデモが崩壊しうる== |
| **法務（7章）** | 特徴量を保存しないと言い切れる | 同上＋会員同意は取得済み前提 | ==個人識別符号扱い。撮影告知・同意・保存期間・削除手段が必須== |
| **提供価値** | 「今この瞬間、4番棚で迷っている」＝**接客タイミング** | A＋常連には履歴提案 | 「前回の続き」＝**関係性の蓄積** |
| **ハッカソン適性** | ◎ | ○ | △ |

### 推奨

**A（完全匿名）をMVPとし、Cは3章に「スコープ外（将来構想）」として明記する。**

理由:

1. [[07-04ハッカソン 課題発見まとめ]] で挙がった酒販店の課題の筆頭は「**新規顧客の獲得が難しい**」。新規客は定義上リピーターではないので、匿名で課題に届く
2. 「特徴量は保存せず退店で破棄」は弱点ではなく、==審査で語れる強み==になる
3. デモは画面内シミュレーションなので、識別レベルはデータ生成側の設定で表現できる。実装難易度を上げる理由がない

> [!warning] 既存ノートとの矛盾に注意
> [[要件定義]] の「**○○さんはこれをよく見てます**」という記述は案C（リピーター識別）を前提にした文。案Aを採るならこの表現は「**客A（滞在4分）はこれをよく見ています**」に置き換わる。ノートの表現を後で直す必要がある。

### 案Aでも失われないもの

- 同一来店中の行動履歴（1→2→3番棚を回って4番で滞留）は完全に取れる
- そこから推定する好みプロファイルも取れる（論点2）
- 失われるのは「前回」の情報だけ

## 論点2: 好み推定（フロントからの要求）

### フロントが表示したいもの

マップ上の客の点に、以下が付随して見える状態が理想:

```
● 客A  ⏱ 4:12
  甘口寄りかも（確信度 中）
  根拠: 3銘柄を長く見た
```

線や点だけのマップでは、==ベテランにしか読めない==。行動を「味の言葉」に翻訳して初めて、新人でも動ける道具になる。これは [[インプットセッション]] の瀬戸氏の課題（消費者の「辛口ください」に応えきれない）への直接的な回答にあたる。

### そのために必要なデータ（バックエンド側の作業）

1. **商品マスタに味覚属性を持たせる**
   - 最低限: 甘辛（日本酒度）、濃淡（酸度・ボディ）、香りの高さ
   - 推奨: **4タイプ分類（薫酒・爽酒・醇酒・熟酒）** を併記。日本酒サービス研究会の標準分類なので、==タグが「なんとなく」ではなく説明可能==になる
   - デモ用なら10〜20銘柄を手入力で十分

2. **座標 ↔ 商品の紐づけ**
   - グリッドのセルに商品ID配列を持たせる（[[要件定義]] のマインスイーパ的マップ構想そのもの）

3. **滞留イベントの記録**
   - `session_id` / `cell` / `開始時刻` / `滞留秒数`
   - 「見た」と「迷った」の境界＝滞留秒数のしきい値をどこに置くかは要決定

4. **推定ロジックの置き場所**
   - **サーバー側計算を推奨**。フロントは表示に専念でき、ロジック変更でフロントを触らずに済む
   - 計算自体は単純: 滞留秒数を重みにした属性の加重平均 → しきい値でタグ化

5. **確信度（confidence）を必ず返す**
   - 滞留イベント数が少ないうちは「推定中」を出したい
   - ==新人が断定表示を鵜呑みにして外す==のを防ぐための、UX上の必須項目

### API のイメージ（フロントが欲しい形）

```
GET /sessions  → 10秒ごとにポーリング
[
  {
    "session_id": "a1b2",
    "x": 3, "y": 5,
    "state": "hesitating",        // moving | viewing | hesitating
    "dwell_sec": 42,
    "profile": {
      "tags": ["甘口寄り", "香り高め"],
      "confidence": "medium",      // low | medium | high
      "basis": ["天狗舞", "手取川", "福正宗"]
    },
    "elapsed_sec": 252
  }
]
```

> [!tip] フロント側の当日リスク回避
> デモが画面内シミュレーションである以上、==上記レスポンスを返すモックサーバー（またはフロント内モックモード）を最初に作る==のが最優先。これがあればバックエンドの完成を待たずにUIを作り切れるし、当日の通信事故でもデモが死なない。

## バックエンド担当に決めてほしいこと

- [ ] 識別レベル: A / B / C のどれか（推奨A）
- [ ] 味覚属性のスキーマ: 数値軸か、4タイプ分類か、両方か
- [ ] 商品マスタのデータ源: 手入力か、外部API（さけのわ等）か
- [ ] 「迷っている」判定の滞留秒数しきい値
- [ ] 推定計算をサーバー側で持つことの可否
- [ ] `GET /sessions` のレスポンス形をこの形で確定してよいか
